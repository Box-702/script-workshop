feat: 主 Agent 按需加载技能（D-14）——触发器留提示词，细则进 app/skills/

D-12 留下的「什么时候该推翻」就是这件事：让主对话 Agent 也按需加载技能。
但直接照搬会错——先看清那 15 条规则是什么：它们是**路由信息**（用户说「出片」该调
哪个工具），每一轮都要用。搬进技能 = 每轮多一次工具往返，而且模型一旦懒得加载
就等于**不会做事**。这不是省 token，是把可靠性押在「模型每次记得加载」上。

真正的缺口不是提示词长，是**提示词太薄**：「长篇小说」那条把五步流程压成一句话；
「出片」那条没写「指定镜头不走接力链」。这些细则只存在于 docs 和代码里，模型看不到。

所以分界线是：**「该做什么」留在提示词，「怎么做 / 什么顺序 / 什么会失败」进技能。**

## 改了什么

app/skills/loader.py
- SkillMeta 增加 audience 字段（crew / main），list_skills / skill_index 支持按受众过滤
- 受众写错（如 `mian`）直接 ValueError 并 log.error 跳过——静默「永不加载」最难查

app/chat/conductor.py
- SYSTEM_PROMPT → SYSTEM_PROMPT_TEMPLATE + system_prompt()：
  触发器表（一行一条）+ skill_index("main") 目录（只有 name/description/when_to_use）
- 新增 load_skill 工具（第 23 个）：只能加载 main 技能；未知名字返回**可读提示 + 可用清单**，
  不抛异常——工具抛错会在当轮消息流里插一条错误，模型连改口的机会都没有
- 用 replace 而不是 str.format 注入目录（延续 D-12 那条：花括号会炸）

四个 audience: main 的技能（约 5.6k 字符，全部来自代码与文档的真实语义）
- novel-serial        长篇分段改编：建图 → 提弧 → 按章选段 → 连载续接与汇报口径
- crew-pipeline       剧组四件事的依赖顺序（提示词硬依赖拆解）与人工审阅边界
- production-delivery 批准前置 / 整片走接力链而指定镜头不走 / 合成时跳过配音≠失败
- script-review       审阅闭环四个动作 + 三条铁律（不替用户决定、汇报以工具为准）

## 为什么不把剧组技能也列进主 Agent 的目录

主 Agent 不执行分镜。列进去既是白付的 token，也会诱导它去加载「导演分镜方法论」
这种它根本不该执行的东西——**目录本身就是一种授权**。

## 验证：先实测，再改，再实测

静态 14 条新测试：受众分组不串味、目录不含剧组技能、14 条触发器逐条指向真工具、
技能「相关工具」必须是真工具、提示词预算 <2400 字、铁律不许丢、audience 写错要吵。

真实模型路由实测（DeepSeek，每例连跑 3 次）：

  二十万字直接要初稿 → 3/3 加载 novel-serial 并拒绝整本生成
  把第 1 场对白改口语化 → 3/3 加载 script-review
  镜头都定好了帮我出片 → 3/3 先只读盘点，动手前加载 production-delivery 再提交
  拆好了吗 → 3/3 只调 check_background_tasks，不加载（纯盘点不该浪费往返）

## 第一次实测就发现写错了

最初的写法只有一句软要求「进入对应领域前先调 load_skill」——实测「出片」**0/3 加载**，
模型把它理解成「先查状态」而不是「要动手了」。改成按**动作**规定顺序（「本轮要动手，
第一个工具调用就该是 load_skill；只读盘点可以先查」）之后稳定 3/3。

教训：**软要求写不进概率模型的行为里。要么给顺序，要么给反例。**
