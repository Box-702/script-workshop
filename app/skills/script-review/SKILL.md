# 改编不会直接改掉剧本

`run_adaptation` 走的是底层工作流：

```
context → plan（ReAct 查原文 / 查版本）→ propose（结构化 patch）
        → guard（硬校验 + 五维评审，不合格回炉，上限 3 次）
        → review（中断，等用户决定）→ apply（落成新版本）→ finalize
```

它产出的是**提议（patch）**，不是新剧本。剧本只有用户接受之后才变。理解这一点，就不会
说错话：生成时说的是「提议好了，请审阅」，不是「改好了」。

# 卡片上的四个动作

| 动作 | 结果 |
|---|---|
| 接受 | 应用 patch，生成新版本 `ver_xxx`；旧版本保留，可回滚 |
| 编辑 | 用户在工作台逐条改，改完再接受 |
| 重新生成 | 带着他的反馈回炉，再出一版提议 |
| 拒绝 | 剧本保持不变 |

这些动作走**确定性路径**（不进 LLM）。用户点了就直接生效——你不要再调工具重复执行一次，
也不要把「用户其实没点」说成「已接受」。

# 三条铁律

1. **不代替用户做决定**。接受 / 拒绝 / 批准永远由用户发起。你可以解释影响、可以建议，
   但不能替他按下去。
2. **汇报以工具返回为准**。说「已生成 ver_xxx」之前，本轮必须真的调用过对应工具；
   版本号只能从工具返回值里取，不许凭历史猜。没调就说还没做。
3. **拒绝之后要问一句为什么**。把原因（哪里不对、想往哪个方向走）带进下一次
   `run_adaptation`，否则同样的提议会原样再来一次，白烧一遍额度。

# 什么时候不该跑改编

- 还没有初稿 → 先 `generate_script`。
- 用户只是问「这个结尾好不好 / 剧本怎么样」→ 用 `get_script_overview` 或 `ask`，
  咨询不是改编，别动剧本。
- 用户要的是整段重写而不是局部调整 → 说明这会走一次完整生成（耗时与额度都更高），确认后再动。
- 用户要改的是**视频提示词**而不是剧本 → 那是 `production-delivery` 的领域，去工作台逐镜编辑。
