# 提示词质量 eval

> 测的是「**提示词质量有没有退化**」，不是「代码有没有崩」。代码正确性由 [`tests/`](../tests/) 负责。
>
> 选型理由见 [`../docs/DECISIONS.md`](../docs/DECISIONS.md) 的 D-13。

---

## 一、为什么需要它

改提示词是**没有编译器的**——改完不会报错，只会在成片里慢慢变差。以前我们只能靠
「出片后肉眼看」发现，这太晚了：一个分镜写坏了，要等视频生成完、拼完、烧完字幕才发现。

eval 把这件事提前到**文本层**：跑一遍真实链路，把导演的分镜和摄影指导的提示词
拉出来，用规则 + LLM 判分当场给出「这次改动是不是把质量拉垮了」。

---

## 二、三层结构

| 层 | 需要 key | 判什么 | 能否进 CI |
|---|---|---|---|
| **L0 单元** | 否 | 断言库自身、judge 解析器、case 完整性 | ✅ 每次都跑 |
| **L0.5 离线回归** | 否 | 用**录制的真实产出**跑断言，锁住「不误报」 | ✅ 每次都跑 |
| **L1 确定性** | 是 | 真实链路的分镜与提示词，规则判定 | ⚠️ 需 secret |
| **L2 judge** | 是 | 同一批产出，LLM 按量表打分 | ❌ 只看趋势 |

**为什么必须有 L0.5**：确定性断言最危险的失败模式是**误报**——一条假告警会让
每个镜头都挂着警告，用户审阅时被反复干扰，告警直接失去意义（这个坑我们真踩过：
审计器曾对真实提示词 4/4 全误报「一镜多运镜」）。L0.5 用录制的真实产出把「不误报」
这条性质锁死，不花一分钱、不花一秒钟。

## 三、怎么跑

```bash
# 只需要 key，不跑 judge（快）
python -m evals.run

# 加 judge 打分（慢、贵）
python -m evals.run --judge

# 只跑几条
python -m evals.run --cases dialogue_tension,single_pressure

# 存 JSON 报告
python -m evals.run --out eval_report.json
```

pytest 方式：

```bash
pytest evals/ -q                    # 没配 key 时 L1/L2 自动 skip
pytest evals/ -q -k case_deterministic
```

**退出码**：`0` 通过 ｜ `1` 未通过（有 critical）｜ `2` 环境问题（没配 key / 余额不足）。

> 余额不足、限流、鉴权失败会被归为 **blocked**（基础设施挡住），
> **不算质量失败**——但会在报告里显式列出。跑不动不能被误读成「跑过了且通过」。

## 四、判定标准

### 确定性层（硬红线）

`critical` 必须为 0。规则表见 [`assertions.py`](assertions.py)：

| 前缀 | 范围 |
|---|---|
| `DIR-*` | 导演分镜：五锚点、function、final_frame、细节密度、接力自洽、时长可行 |
| `DPT-*` | 摄影提示词：空洞词、否定句、引用台词、锚复用、细节密度、运镜、光源/光位与分镜是否一致、同句重复 |
| `LNG-*` | 跨链路：镜头集合对得上、场景没漏、每镜都有提示词、分镜光线与风格指南不打架 |

`warn` 只报告不拦截（多运镜、锚被轻微改写等质量风险）。

### judge 层（趋势）

量表见 [`rubric.md`](rubric.md)：戏剧性 25% / 可渲染性 25% / 一致性 20% / 具体度 15% / 克制度 15%。

**judge 分数不参与红绿判定**——LLM 打分有抖动，10 条样本也不够做统计判定。
它负责回答「这次改动之后，整体是变好还是变差」。

- 单条 case 波动 ±5 分 = 噪声
- 超过 8 分 = 真回归，要查
- 均值跌破 75 = 质量拉垮了，要回滚或重写提示词

## 六、怎么加一条 case

1. 在 `cases.py` 里写一个 `EvalCase`：给一份**有真实戏剧张力**的微型剧本。
   - 别用「场景1 / 角色A」这种假数据——假数据测不出质量，只能测出代码不崩。
   - 一到两场就够，控制单次 eval 的成本。
   - 在 `watch_for` 里写清这条 case 特别关注什么（写帮助人判断失败重不重要）。
2. 加进 `ALL_CASES`。
3. 跑一遍 `python -m evals.run --cases <新 case id>`，看看真实产出长什么样。
4. 如果断言报出的问题**确实是问题**（不是误报），说明规则该保留；
   如果是误报，先修断言（并且在 `tests/test_dramaturgy.py` 里补一条回归测试）。

## 七、已知限制

- **LLM 输出不确定**：即便把温度钉到 0，同一 case 两次跑出的分镜也不完全一致。
  对策：出现 critical 时**自动复跑一次**，两次都失败才算稳定缺陷。
- **样本量小**：10 条 case 只够抓明显的退化，不够做细粒度的统计显著性判断。
- **judge 有偏**：它看到的就是视频模型看到的提示词（包括每镜都带的全片风格段），
  所以风格段本身的问题会压低「克制度」维度分——这**不是 judge 的偏差，是真问题**。
- **provider 相关**：提示词方言随目标 provider 变。换 provider（Kling / Sora / …）
  需要另跑一轮，`--provider` 参数已留好。
